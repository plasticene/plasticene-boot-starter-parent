# FLOW 旧接口迁移与存量表单元数据补齐

日期：2026-11-16。状态：基于用户最新事实收敛后的具体方案，尚未实施。关联[完整改造方案](flow-boundary-proposal.md)。本稿替代此前针对未知外部调用和混用历史的假设性设计，不再保留那些分支。

## 1. 已确认事实

- 当前没有外部真实 API 调用，没有服务引用该框架。
- 每个发布定义只使用一种表单类型；模型设计态允许切换，重新发布后对新申请生效，历史定义与运行实例保持不变。
- 现存历史数据全部使用 FLOW 自带表单。

## 2. 旧 API 处理

直接将已知示例、测试和 Controller 迁到按职责组织的公开接口，然后移除 FlowEngine/FlowEngineImpl，不保留一个发布周期的弃用委派层。

REST 模块直接更名为 plasticene-flow-rest，同步内部依赖和文档，不提供旧坐标 relocation、旧实现 Jar 或类名兼容桥。旧无组织人员方法、事件专用授权策略在迁移现有内部接入后收敛至目标契约，不保留双路径。执行内核覆盖按已确认方向废止。

影响：内部示例与测试一次调整，避免今后维护重复 API。前端现有 HTTP 路径、响应及 varMap 字段仍按主方案保留；没有外部调用不等于可以漏改当前前端。

## 3. “历史回填”具体指什么

是新结构上线时，为已有数据库行补新增字段的值，不是补业务内容。

| 已有记录 | 新增字段 | 拟补的值或来源 |
| --- | --- | --- |
| flow_model | form_mode | 建议编码 0（FORM），因为所有既有模型都使用自带表单 |
| flow_definition | form_mode | 建议编码 0（FORM），因为所有既有发布定义都使用自带表单 |
| flow_definition | var_info | 从这一行自己的 form_config 提取字段键、名称、类型及可可靠确定的约束，形成变量定义快照 |

示例：某发布定义原表单有 amount 数字字段。新结构增加 var_info 后，需要存入“amount 是 NUMBER”这一元数据；某实例已提交 amount=5000 的值原样保留，不从业务库重取，不把它改成其他值。

不修改 flow_instance.varMap，不重算已完成审批路径，不改 definitionId，不重写表单变更记录和事件载荷。实例继续通过已有 definitionId 取得对应变量定义，无需额外实例模式字段。

必须使用各历史发布定义自己的表单配置，不使用当前模型的最新版配置覆盖旧版本。未发布草稿设计时仍可从自身 formConfig 获取变量定义，不必另给模型保存重复的发布快照。

## 4. 实际补齐步骤建议

1. 增加模式和定义快照字段，现有数据保留。
2. 将既有模型和发布定义的模式统一补为 FORM。
3. 按发布定义逐条读取其 form_config，复用与新发布相同的表单到变量定义转换规则，生成 var_info。
4. 核对字段引用、类型、已有条件和权限配置的一致性，再收紧新增字段约束并启用新校验。

纯常量模式字段可由增量 SQL 补齐；表单 JSON 结构较复杂时，推荐发布一次性、显式执行的数据转换工具或处理脚本，与 SQL 部署文档配套，不能当成 Starter 每次启动的自动动作。具体实现语言和调用方式在看到实际配置后确定，不新增迁移框架依赖。

如果现有表单配置有缺失或旧格式，针对这些记录列清并调整转换，不凭空补默认类型，也不预先设计一整套历史兼容引擎。这不是业务模式混用问题。

## 5. 变量编码仍需细化的范围

- 字段键保持原值，不自动改名、trim 或大小写转换；名称与字段键分开。
- 保留现有 FieldTypeEnum 编码及运算语义；新变量定义应先适配现有表单实际支持的输入，不迫使全部现有表单控件退化为字符串。
- NUMBER、DATE、COLLECTION 的新输入规则与当前前端取值、Java 调用及运算器一起核对。日期沿用现有 yyyy-MM-dd HH:mm:ss，条件 inputValue 字符串协议不和 varMap 值混淆。
- 子表单、附件等不参与条件计算的内容字段，需要明确保留与校验路径，不能简单因未出现在条件变量列表就丢弃或拒绝整个表单。
- 新严格校验只在实际规则确定后落地，避免把存量表单合法数据误判为未知字段或错误类型。

## 6. 明确删除的设计

不做外部 API 兼容期、旧坐标迁移桥、历史业务契约恢复、模型拆分、逐实例模式推断、legacy_mixed、legacy_form_mode、历史实例重关联、旧流程取消重发或新旧引擎并行处理。

本轮仅更新方案；不生成或执行 SQL，不改代码、POM、运行配置或数据库，不删除既有数据。

后续同一模型的新版本可以切换类型；这不需要拆分模型，也不改变上述存量 FORM 元数据补齐规则。迁移和运行均按发布定义处理，不用模型最新类型覆盖旧定义。
